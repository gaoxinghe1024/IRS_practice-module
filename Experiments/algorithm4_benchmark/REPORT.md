# Algorithm 4 — RAG Evaluation for the AnimeFinder Page-4 Chat

> **Scope.** Algorithm 4 evaluation: chat to find anime with an LLM, a knowledge
> base and RAG. System under test: the AnimeFinder v1.4.1 Page-4 chat pipeline,
> `backend/services/rag.py` (git blob 3b5f6dc; commit 426db20 of the team
> repository), frozen in `algo/rag_snapshot.py` with its 24-title seed knowledge
> base and 12 scenes. The AniLogic chat in `app/chat` is not part of this run:
> the method (R/N/T conditions, scoring, bootstrap CIs) carries over, the
> numbers do not.

**Dates**: main experiment 2026-09-29; R+ field-completion follow-up 2026-09-30; all statistics are computed from the saved raw outputs (no further model calls after the 48-call R+ stage) · **Channel**: A (CodeBuddy CLI 2.158.0, headless) · **Calls**: ≈1,260 / 1,800 cap (+ 48-call R+ follow-up)

**Scope of what was executed.** The system's own code (retrieval, prompt construction, template reply) was run as a Python module from a copy of the repository; it was not run as the deployed service (no frontend, no HTTP layer). The six models' answers and the three judges' scores were produced through the CodeBuddy CLI channel, not through vendor API keys, so the system's own `_llm_reply` network path was never executed (its request was intercepted only to capture the exact prompt). Absolute scores, latencies and timeout rates therefore should not be read as end-to-end results for the deployed system with a given vendor key; relative comparisons hold within this single channel.

## Objective

Quantify how much retrieval-augmented generation (RAG) improves the "chat-to-find-anime" feature (Page 4) of AnimeFinder, and whether the template pipeline (T) should be kept. Six built-in LLMs were tested with RAG (R) and without (N) on **80 test queries (74 Chinese, 6 English)** across six question types: scene identification (24), constraint filtering (16), trap/false-premise (12), similar-anime (10), mood (10), and factoid (8).

## Key findings

1. RAG raises the judge score by **+0.41 to +0.67** on the 1–5 scale (n = 80 paired questions × 6 models); after removing the faithfulness dimension the lift is significant for **3 of 6 models** (GLM-5.3, GLM-5.3-Flash, MiniMax-M3), and after controlling for answer length for 4 of 6 (Kimi edge-significant at [+0.011, +0.402]).
2. KB-consistent episode accuracy on scene questions rises **+0.36 to +0.64** (R 0.86 vs N 0.39, n = 132 scored replies); all-constraints-satisfied rises +0.31 to +0.44 for 3 of 6 models (n = 16 constraint questions × 6).
3. The only significant regression is factoid: **−0.50 to −0.62** (rule-scored accuracy, n = 8 × 6); per-cause classification shows **all 29 flips come from the named work not appearing in the R prompt's knowledge-base text** (category ①: 29; "work present but field missing": 0; "both present, still wrong": 0). **18 of the 80 questions name a KB work by title or common short name (8 factoid, 10 similar); the 6 scene questions match only generic nouns or character names and are not counted as naming.** The named work is present in the prompt text for only **3 of 8 factoid and 4 of 10 similar questions** — **absent for 11 of 18 (10 pushed out of the top-5 candidates by mention-demotion, 1 removed by the constraint filter; by type: fact 5, similar 6)**, and present for the other 7 (4 as an own work-entry row, 3 only via famous-scene lines).
4. KB-citation compliance: after removing echo (the query's own title repeated in refusals) and in-KB title variants, **0 of 480 R replies recommend an out-of-KB title without disclosure** (the 10 R replies that keep a residual out-of-KB title after that removal are reviewed one by one in `results/extra/out_of_kb_review.csv`); R's out-of-KB reply rate is 0.00–0.05 — the metric is constraint compliance, not quality. Reply-level in-KB citation rate: 0.94–1.00 in R vs 0.20–0.38 in N (paired lift +0.59 to +0.80).
5. Frank rate (declaring missing information instead of fabricating; fixed-regex definition): R−N = **+0.62** overall (n = 66 paired replies; question-cluster 95% CI [+0.3485, +0.8939], 11 questions), **+0.31** excluding the real_not_in_kb slice (n = 36; descriptive; question-cluster 95% CI [0.0000, +0.6389]), **+1.00** for that slice alone under the rule caliber (judge sensitivity +0.97; n = 30, exploratory; it is a scope policy, not honesty).
6. T (system default) scores **2.44** overall but **2.06 on scene / 2.60 on non-scene** — judged on reply text only (scene bubbles invisible to judges), so it is a lower bound, not the page experience.
7. The centered ranking is **two-tier**: GLM-5.3-Flash, GLM-5.3 and Kimi are each significantly above MiniMax-M3, Deepseek and Hy3 — **9 of the 15 pairwise gaps are significant, and they are exactly the 9 cross-tier ones** (Kimi−MiniMax [+0.009] and Kimi−Deepseek [+0.002] are marginal); **no gap is significant within either tier**. No multiple-comparison correction was applied to the 15 tests; the raw-score spread is narrow (3.99–4.12) and raw ranks flip after centering, so ranks within a tier should not drive decisions. Hy3 is statistically tied with Deepseek (Deepseek−Hy3 = +0.020, n.s.) and MiniMax (MiniMax−Hy3 = +0.058, n.s.) — same bottom tier, no quality edge. Cost: RAG adds ≈+337 to +406 net input tokens per query; output-token reductions are mostly reduced reasoning tokens and are not "cost saved".

## System under test

- **R (RAG)**: the production `rag.py` retrieval pipeline (lexical matching, scene-intent threshold 0.34) feeding retrieved knowledge-base snippets into the prompt. The system's real LLM request is a single user message with `temperature: 0.6`, no `max_tokens` and a 20-second timeout; this evaluation ran through the CLI channel, where **none of these settings take effect the way the system sets them** (temperature is not settable; there is no 20-second timeout — the >20 s figures are post-hoc statistics, not enforced cutoffs).
- **N (LLM only)**: same models, raw prompt, no retrieval.
- **T (system default)**: the output of running the real `rag.chat()` (a working copy of the repository, no LLM env vars set) once per test query, verbatim identical to the stored T answers (prompt-fidelity check: 80/80); not a deployed service (no frontend or HTTP layer).
- **Knowledge base**: 24 anime titles, 137 aliases, curated famous-scenes store.

## Experimental setup

- **Models** (display ↔ CLI id, all verified via server-side `requestModelId` echo): Hy3 ↔ `hy3`; Deepseek-V4.1-Flash ↔ `deepseek-v4.1-flash`; GLM-5.3 ↔ `glm-5.3`; GLM-5.3-Flash ↔ `glm-5.3-flash`; MiniMax-M3 ↔ `minimax-m3`; Kimi-K3 ↔ `kimi-k3-1`.
- 160 calls per model (80 questions × R/N), single repetition; 960 generation calls + 240 judge calls + ≈60 probes; plus the R+ field-completion experiment (8 factoid × 6 models = 48 calls). All analyses in this report are computed from the saved outputs; no model calls were made after the generation and judging stages.
- **Judges**: 3 LLM judges (Hy3, Deepseek-V4.1-Flash, GLM-5.3) scoring listwise over 13 candidate answers per question (T + 6 models × R/N); candidate order re-randomized per judge per question (seed 42); same-vendor judges excluded when scoring a tested model (`judge_avg`; an all-judge average is also reported).
- **Statistics**: 95% CIs from 10,000 paired bootstrap resamples (seed 42). RAG lift = paired per-question R − N differences.
- **Known deviations**: CLI injects a system prompt (≈2,976 hidden input tokens, an estimated value); temperature/max_tokens not settable; single run; T is the verbatim output of the real `rag.chat()` (see System under test). The glm-5.3 stream resumed across 3 passes after an early interruption (cause unproven from retained artifacts; no 429 records retained).

### RAG lift by metric

Judge score **+0.41 to +0.67** (n = 80 × 6; 3/6 significant after dropping faithfulness, 4/6 after length control); KB-consistent episode accuracy on scene questions **+0.36 to +0.64**; all-constraints-satisfied **+0.31 to +0.44** (3 of 6 models, others positive n.s.); **frank rate** +0.55 to +0.64 per model over all trap replies under the fixed-regex rule definition (aggregate +0.62, n = 66) — with the real_not_in_kb slice (+1.00 alone under the rule; +0.97 judge caliber) treated as scope policy and reported separately, the remaining traps improve by **+0.17 to +0.33** per model (+0.31 aggregate; judge caliber as sensitivity: +0.62 / +0.33 / +0.97; the T10 offtopic question is reported separately). The two aggregate frank figures (+0.62 / +0.31) pool all six models; question-level cluster bootstrap CIs are in `results/extra/frank_aggregate_cluster.csv` (for the +0.31 slice the 95% CI reaches 0 — six questions only, wide interval). In-KB citation compliance (reply-level; echo titles and in-KB variants removed, at least one work title recognized): 0.20–0.38 in N → **0.94–1.00 of replies in R**, paired lift **+0.59 to +0.80**. Scene Top-1 shows no lift (ceiling: 0.75–0.83 in N already). Mood questions trend negative (n.s.).


### Factoid regression

The only significant regression: fact accuracy **−0.50 to −0.62** for all six models (rule-scored, n = 8 × 6; final scorer: R 19/48). Root cause = **retrieval recall, definitively**: the named work is absent from the R prompt's knowledge-base text for **5 of 8 questions**; per-cause classification puts **29 of 29 R−N flips in "named work not in context"**, with zero flips where the work was present (F03/F04/F06 are answered correctly by all six models). The R+ field-completion experiment (48 calls) recovers nothing net (**19/48 vs 19/48**), because the named works are not in the prompt text in the first place. Models follow the "answer only from the KB" instruction and refuse — on the 30 R replies where the named work is absent from the prompt text, **29/30 are scored wrong; the remaining 1/30 (F07 × Kimi-K3) declares the work missing ("EVA is not in this knowledge base") yet still gives the correct year (1995) from common knowledge, clearly marked as such, which the scorer counts as correct**. That is false absence, not fabrication.

### Retrieval layer

Hit@1 **87.5%** / Hit@3 **91.7%** on scene questions (easy: 100%/100%; hard: 75%/83%). The scene intent fires on only **8.3% of hard (paraphrased) scene questions** (threshold 0.34) — **but intent does not gate what the LLM sees**: `_build_context` unconditionally appends the top scene hits, and the standard scene text is present in **12/12 easy and 10/12 hard R prompts**. What the threshold controls is the frontend "memory bubble" (system-level scene-focus accuracy: easy 11/12, hard 1/12) and the template reply branch. **Threshold tuning alone cannot fix it**: sweeping t = 0.10–0.50, no threshold both raises the hard trigger rate materially and keeps non-scene misfires ≤ 5% (`results/figures/fig4_threshold_sweep.png`). Constraint extraction: 62% key recall (23/37), 100% value accuracy when extracted; `tags_any`-type genre constraints are dropped; English constraint phrases do not match the Chinese regexes. Non-scene misfires: **2/56 = 3.6%** (C02, F03). **Named-work recall failure (generalized)**: 18 queries name a KB work by title or common short name (fact 8, similar 10; the 6 scene questions match only generic nouns or character names and are not counted as naming). Unified caliber — **does the named work appear in the R prompt's knowledge-base text** (what the LLM actually sees: top-3 work entries + famous-scene lines; per-question table `results/extra/named_recall_per_question.csv`, also Appendix E below): **present 7/18 = 4 as an own work-entry row + 3 only via a famous-scene line (X01, X02, X05); absent 11/18 = 10 pushed out of the top-5 candidates by mention-demotion (fact 5, similar 5; candidate positions 7–23, e.g. F07 → 20, X09 → 23) + 1 removed by the constraint filter before ranking (X10)**. The work-entry row is a subset of the top-5 candidates for all 18 named questions. The mention-demotion step (`rag.py` L146-153) is **intentional design for similar-type queries** — on recommend-intent queries it moves the work the user named to the end of the candidate list so the system does not recommend it back; the same step applies to every recommend-intent query, so for factoid and scene questions it acts as a defect and is the main cause of the misses. This drives the factoid regression and **43 false-absence declarations in the R group over the 18 named questions (fact 27, similar 16; N group: 0)** — replies stating the KB lacks the named work ("the KB doesn't have X" for in-KB X); a declaration counts as **strictly false** when the named work was in fact present in the prompt text (1 of the 43: X05 × Hy3; per-reply table `results/extra/false_absence_per_reply.csv`). The same regex also fires on 6 scene replies, but those are "this episode/scene is not in the KB" statements whose replies already name the answer work, and the answer work is in the R prompt's KB text for all 6 scene questions — scene is therefore outside the false-absence caliber.

### Tokens

RAG adds **≈+337 to +406 net input tokens per query** (input = CLI-reported tokens incl. cache read/write; net input = input − hidden overhead, estimated per model by OLS regression of input tokens on prompt character count, intercepts 2,962–3,036, R² ≥ 0.998 — **except MiniMax-M3, unreliable (R² = 0.28, fallback 2,976)**; token counts use each model's own tokenizer and are not strictly comparable). Output tokens fall by 106–1,415, but **80–95% of the reduction comes from reasoning tokens** (visible answers shorten by only 117–189 characters); since N and R use different prompts, this should **not be generalized as "RAG saves tokens"** — and "net total" is not used as a cost proxy (tokens are not cost). Total recorded usage is **≈6.4 M tokens (4.81 M in + 1.58 M out; ≈6.6 M including the 48-call R+ stage)**, a lower bound; per-stage breakdown in `results/extra/token_cumulative_by_stage.csv`.

### Latency

> 20 s calls drop to 0–15% in R vs 11–40% in N (CLI-measured, including process startup and rate-limit waits; see table in Model quality). Latency-sensitive picks should read the p95 column, not the mean.

## System issues found (recorded, not fixed)

1. Scene-intent threshold 0.34 rarely fires on paraphrased scene queries (8.3% on hard) — affecting the frontend bubble and template branch, **not** what the R-group LLM sees.
2. The `source` field reflects **configuration, not the actual generation channel** (`rag.py` L239): it reads "llm" whenever LLM env vars are set and the reply is non-empty, even if the reply came from the template fallback.
3. **Silent fallback direction is LLM → template** (`rag.py` L238, timeout 20 s at L224, bare except at L227–228): LLM failures are replaced by template replies with no warning; retrieval itself has no such fallback.
4. The 20-second timeout is hostile to slow models — R-group p95 / >20 s share: Deepseek **8.1 s / 0/80 (0%)**, GLM-5.3 15.6 s / 2/80 (2.5%), Hy3 19.1 s / 4/80 (5.0%), Kimi 19.7 s / 3/80 (3.8%), GLM-5.3-Flash 20.5 s / 6/80 (7.5%), **MiniMax 32.4 s / 12/80 (15.0%)** (CLI-measured; N-group figures reported separately).
5. The T template answers trap questions confidently off-topic and appends marketing copy ("tap the card below"); it has no refusal path (T was judged on reply text only — scene-bubble content was not visible to judges).
6. **Named-work recall failure** (upgrade of the factoid issue): of the 18 queries naming a KB work, the named work is **absent from the R prompt's KB text for 11 of 18** (fact 5, similar 6); it is **present for the other 7 of 18 — 4 as an own work-entry row and 3 only via a famous-scene line**. Mechanism (per-question table): for **10 of the 11 misses** the **mention-demotion logic at `rag.py` L146-153 pushes the named work's candidate entry out of the top-5** (candidate positions 7–23; their retrieval scores are non-zero), and the remaining miss (X10, similar) is removed by the constraint filter before ranking. The demotion itself is **intentional design for similar-type queries** (the comment in `rag.py` says the user asked for "similar", not the named work itself) — but it fires on every recommend-intent query, so for factoid and scene questions it acts as a defect. The mention check is substring matching, so a common noun that coincides with a work's Chinese title also fires (in the scene question S03h, 怪物 matches Monster — that work's candidate entry is pushed from rank 1 to 23; the reply is unaffected because the answer work's entry is the first work row in that prompt). Recorded as a defect, not fixed. This produces **43 false-absence declarations in the R group (fact 27, similar 16; N group: 0)** and the entire factoid regression. Field gaps (studios/aired/an_type absent from `_build_context`) never caused a flip by themselves.
7. Genre (`tags_any`) constraints never become retrieval conditions, capping constraint-question gains.
8. **English queries**: title-level matching works (F03 scene score 0.545), but constraint extraction and genre/mood matching are Chinese-only and fail on the 6 English questions (see Appendix C).

## Limitations

- KB covers only 24 famous titles the models already know, muting measurable RAG gains (ceiling effects) and possibly exaggerating the factoid regression (N's 48/48 factoid accuracy benefits from famous titles; may not hold for niche works).
- The test set is author-written; the hard subset is deliberately paraphrased, so the 8.3% intent trigger rate is a stress-test number, not a traffic estimate.
- The famous-scenes store is curated; two titles (S08, S12 — Fullmetal Alchemist: Brotherhood ep. 4; Your Lie in April ep. 21) are **suspected** to differ from the real animations, each with an easy and a hard phrasing (S08e/S08h/S12e/S12h). Scoring follows the KB by contract. Sensitivity uses a **cluster bootstrap that resamples whole questions** (each draw carries all six models' replies for that question; 10,000 resamples, seed 42): on all 22 scored scene questions (n = 132 replies per group) the R−N lift is **+0.470 [+0.303, +0.629]** (R 0.856, N 0.386); excluding all four disputed phrasings (n = 108) it is **+0.426 [+0.241, +0.611]** (R 0.852, N 0.426) — both still significant (lower bound > 0); per-question rates and the exact intervals: `results/extra/scene_sensitivity_cluster.csv`. Flagged for in-team verification. T is the verbatim output of the real `rag.chat()`, not the deployed service.
- Title extraction treats a quoted character name, an episode or song title, or a truncated title inside 《》 as a title, so out-of-KB counts are an upper bound: 10 of the 480 R replies keep such a residual after echo and variant removal, and none is an undisclosed out-of-KB recommendation (`results/extra/out_of_kb_review.csv`).
- Agent/CLI pollution: 16 replies contain leaked tool-call/platform markup (7.5% of Deepseek N replies) and were passed to judges verbatim; excluding those pairs, all six models' R−N stays significant but **Deepseek's lift drops from +0.42 to +0.28 and it swaps last place with Hy3** — ranks below 4th are not robust.
- Single run (repetition 1); CI does not capture full output stochasticity. LLM judges with no human ground truth (judge–human agreement has not been measured); within-question inter-judge rank correlation is only 0.54–0.73, and mean-centering changes the ranking. The faithfulness dimension structurally favors R (N has no KB), and the R/N contrast bundles "KB content" with the "answer only from the KB" instruction.
- Length confound: shorter answers score higher within questions; after length control, R − N is significant for 4/6 models (Kimi edge-significant).
- Token usage figures are as recorded by the CLI in this run (per-model tokenizers, not strictly comparable); the cumulative total is a lower bound (probe stage left no usage records).


## Recommendations

1. **Keep RAG on Page 4** *(verified)*: judge score +0.41 to +0.67 (n = 80 × 6; 3/6 models after faithfulness removal), KB-consistent episode accuracy +0.36 to +0.64, all-constraints-satisfied +0.31 to +0.44 (3 of 6 models), frank rate **+0.31** excluding the real_not_in_kb slice (descriptive; question-cluster 95% CI [0.0000, +0.6389] — six questions only, wide interval) — that slice alone is +1.00 (R refusing out-of-KB real titles is a scope policy, not honesty), so it is reported separately and not counted toward the honesty gain — at a cost of ≈+400 net input tokens per query. No metric shows a significant regression except factoid (mood trends negative, n.s.). In-KB citation rate is a **scope-compliance metric** (R is instructed not to mention out-of-KB titles), not a quality metric. *But*: **until named-work recall is fixed, do not route factoid questions through RAG** (or adopt Recommendation 3's prompt change).
2. Model choice is scenario-conditional (all figures from the table above) *(caliber: centered judge scores; numbers verified, the choice itself is judgment)*. The centered ranking is **two-tier**: GLM-5.3-Flash / GLM-5.3 / Kimi significantly above MiniMax / Deepseek / Hy3 (9 of 15 pairwise gaps, all cross-tier; no correction for multiple comparisons; no significant separation inside either tier, so ranks within a tier should not drive decisions). Quality-first → GLM-5.3-Flash or GLM-5.3 (centered 0.45/0.44); latency-critical → Deepseek (0/80 calls over 20 s, p95 8.1 s) — it shares a vendor with the system default (`deepseek-chat`) but is **not the same model**; stable quality → Kimi-K3 (centered 0.43, 3/80 over 20 s). **Hy3 sits in the same bottom tier as Deepseek and MiniMax** (statistically tied with both: Deepseek−Hy3 = +0.020 and MiniMax−Hy3 = +0.058, both n.s.) **and has no quality edge over them**; the factual reasons not to pick it: highest output tokens per R call (790), p95 19.1 s (4/80 over 20 s), and under the contamination sensitivity (ranking by R−N lift) it swaps last place with Deepseek. Lowest output tokens per R call: **Kimi-K3 (277) / GLM-5.3 (305) / GLM-5.3-Flash (313)**; then MiniMax-M3 (528), Deepseek (628), Hy3 (790) — the levels, not the R−N deltas, are what matters for a token budget. Avoid MiniMax-M3 for real-time chat (12/80 calls over 20 s, p95 32.4 s); its input / net-input token columns come from an unreliable regression (its output-token reading is fine). Cost = token usage × vendor prices, to be computed by the team; this report deliberately gives no amounts.
3. **Fix named-work recall** — scope: all queries naming a KB work (n = 18: similar 10, fact 8; the named work is absent from the R prompt's KB text for 11 of them — fact 5, similar 6) *(root cause verified: mention-demotion pushes the work's candidate entry out of the top-5 for 10 of the 11 misses (12 queries are demoted in total; X01 and X05 still reach the prompt through a famous-scene line) — intentional for similar queries, a defect for fact/scene — and the constraint filter removes it for 1 similar question (X10); see System issue 6; the fix itself is not)*: recall first (exact-title match weighting in the scorer / pin named titles to the top), field completion second (R+ shows fields alone do not help; models can sometimes infer the answer from other fields). New option: change the prompt from "answer only from the knowledge base" to "answer from the retrieved entries (not the whole KB); when an entry lacks the answer, say so and you may add common knowledge, clearly marked". **Whether recall + fields together remove the regression: unverified** (R+ tested fields only); an R++ experiment (force the named work into the prompt context and add fields, ≈48 calls) could verify it — not run. The short-term fallback "route factoid LLM-only" remains **unverified** and leans on N's 48/48 coming from famous titles (Limitations §1).
4. Scene-intent triggering cannot be fixed by threshold tuning alone (`results/figures/fig4_threshold_sweep.png`); add synonym/semantic matching or rule fallbacks for "which episode" phrasings.
5. Keep the template pipeline only as an offline fallback (no-key mode) **after adding a no-match / low-confidence branch** — it must learn to say "the KB doesn't have this" instead of answering off-topic with marketing copy.
